# 01. 設計判断の記録（ADR）

形式: 背景 → 決定 → 理由 → 代償 → 見直し条件。
変更時は上書きせず新しい ADR を追加し、旧 ADR に「Superseded by ADR-xxx」と書く。

---

## ADR-001 Web 技術（Three.js + TypeScript）で作り、iPad Safari で遊ぶ

**状態**: 採用（2026-10-03）

**背景**: 最大の失敗要因は「放置」。開発ループの摩擦を最小にし、生成 AI が自律的にビルド・検証・配信まで
回せる構成が必要。遊ぶ端末は iPad Pro 2021（M1）。

**決定**: Three.js（WebGL2）+ TypeScript + Vite。GitHub Pages に配信し、Safari で PWA として起動する。

**理由**:
- Xcode / Mac / Apple Developer 登録 / 実機署名が不要。push すれば iPad で URL を開くだけ
- 全資産がテキストまたは標準フォーマット（TS / JSON / glTF）で、AI エージェントが扱える
- クラウド環境からビルド・テスト・ヘッドレス描画の目視確認・デプロイまで完結する
- 本人の過去プロジェクト（ブラウザ + AI 駆動開発）と同じ型

**代償**:
- 性能上限はネイティブ（Unity 等）より低い。ただし M1 iPad とデモ規模なら 60fps は十分可能
- Safari 固有の制約（音声解放、フルスクリーン API 不可、メモリ上限、タッチの既定動作）
- Unity のアニメ調シェーダ資産（UniVRM, lilToon 等）は使えない。トゥーン表現は自前で組む

**検討した代替**:
- Unity: 業界標準でアニメ調資産が最も豊富だが、iPad 実機に乗せるまでの距離が長く、
  エディタ依存資産を AI が扱いにくい
- Godot 4: テキスト資産で魅力的だが iOS 書き出しは Mac/Xcode 必須、Web 書き出しは iOS Safari で不安定
- Babylon.js: 妥当だが、アニメ調キャラ（VRM 等）周辺の資産は Three.js の方が厚い

**見直し条件**: Safari の WebGL 性能や安定性がデモ規模でも不足した場合。

## ADR-002 WebGL2 で開始し、WebGPU は後から検討

**状態**: 採用（2026-10-03）

**決定**: `WebGLRenderer` と既存のポストプロセス資産を使う。レンダラ初期化は 1 箇所に閉じ、
マテリアルは自前のトゥーンマテリアル経由でのみ生成し、将来 WebGPU 版へ差し替え可能にする。

**理由**: iPadOS 26 以降の Safari は WebGPU に対応するが、Three.js の WebGPU 経路は周辺資産
（ポストプロセス・サンプル）が WebGL 経路より薄い。デモ完成を優先し、安定経路を取る。

**見直し条件**: デモ完成後、性能余力が欲しくなった時。

## ADR-003 物理エンジンは入れずに開始

**状態**: 採用（2026-10-03）

**決定**: 衝突は XZ 平面上のカプセル（円）同士と、アリーナ境界、地面高さの取得のみ。自前実装。

**理由**: アリーナ型のキャラクターアクションに必要なのは「キャラ同士が重ならない」「壁を越えない」
「攻撃判定の重なり」であり、剛体シミュレーションは不要。Rapier 等は WASM 読込と同期層を増やす。

**代償**: 坂・段差・ラグドール・物理的な押し合いは出来ない。

**見直し条件**: 段差のある地形、物を投げる・壊す、ラグドール死亡演出が欲しくなった時 → Rapier を検討。

## ADR-004 固定タイムステップ + フレームデータ駆動の戦闘

**状態**: 採用（2026-10-03）

**決定**: シミュレーションは 60Hz 固定（`step(dt=1/60)`）、描画は `requestAnimationFrame` に従い
補間する。攻撃は「発生 / 持続 / 硬直 / キャンセル受付」をフレーム数で定義する。
ヒットストップは時間スケール（`timeScale`）で実装し、UI やカメラは影響を受けない別の時間を持つ。

**理由**: 端末や rAF レート（60/120Hz）の差で手触りが変わらない。戦闘ロジックが純粋関数化でき、
vitest で検証できる。

## ADR-005 キャラクター資産の経路: Tripo を主、VRoid を保険

**状態**: 暫定採用（2026-10-03）。生成と取り込みの手順は ADR-010 で自動化経路に置き換え（Tripo 系の 3D 化を主とする方針は維持）。プレイヤーの採否は M1 の検査で確定する。

**背景**: 本人は画像生成（ChatGPT）→ Tripo（画像→3D）でキャラを作れる。Tripo クレジットは潤沢。
VRoid Studio（VRM）はアニメ顔・髪の揺れ（SpringBone）が標準で、three-vrm で忠実に描ける反面、
デザインの自由度が低い。

**決定**:
- 敵・ボス・小物・環境オブジェクト: **Tripo**（本人が重要キャラの原案を作り、それ以外は AI が順次作る）
- プレイヤー: Tripo で 1 体作り、`03-asset-pipeline.md` の検査基準で判定。
  合格 → Tripo 経路で確定。不合格 → VRoid（VRM + three-vrm）に切り替え、敵は Tripo のまま
- どちらの経路でも、描画は自前トゥーンマテリアルに統一する（MToon 固有の見た目に依存しない）

**懸念（確率順）**: 顔が横から見て破綻する / 関節変形が汚い / 髪・布が揺れない / テクスチャに陰影が焼き込まれている。
対策は `03-asset-pipeline.md`。

## ADR-006 タッチ専用の操作系

**状態**: 採用（2026-10-03）

**決定**: 横持ち iPad、両親指操作。左半分: 浮動仮想スティック（触れた位置が原点）。右半分: ドラッグで
カメラ回転、右下に攻撃（大）・回避・ロックオンのボタン。ロックオン中はカメラが対象を自動で捉える。
コントローラ・キーボードはデモ完成まで対応しない（開発用のキーボード操作は入力抽象化の裏で許容）。

**理由**: タッチではカメラ操作が最大の負担。ロックオンと自動追従で「カメラをいじらなくても戦える」
ことを基本にし、ドラッグは補助とする。

**詳細**: `04-controls.md`

## ADR-007 配信は Vercel（GitHub Pages は使わない）

**状態**: 採用（2026-10-03）。当初案（GitHub Actions → GitHub Pages）を置き換え

**経緯**: 当初は GitHub Pages を想定したが、リポジトリが private で Pages が使えず、
本人が Vercel を接続して iPad 実機で動作確認した（操作感は問題なし）。リポジトリは後に public 化された。

**決定**: 配信は Vercel のリポジトリ連携（push で自動デプロイ、ビルド基点は既定の `/`）。
GitHub Actions（`.github/workflows/ci.yml`）は typecheck / test / build で `main` を守るだけにする。
`vite.config.ts` の `BASE_PATH` 環境変数は、将来 Pages 等に載せたくなったとき用に残す。

**注意**: リポジトリが public のため、資産（Tripo 生成物等）とコードは誰でも読める。
API キー・トークンは絶対にコミットしない（`docs/05-asset-automation.md` 参照）。

## ADR-008 UI は DOM/CSS、フレームワークなし

**状態**: 採用（2026-10-03）

**決定**: HUD・メニュー・仮想ボタンは素の DOM と CSS。React 等は入れない。

**理由**: ゲームループ側は命令的な更新が自然で、UI の規模も小さい。依存を減らす。

## ADR-009 トゥーン描画の方針

**状態**: 採用（2026-10-03）

**決定**:
- 全オブジェクトに自前のトゥーンマテリアル（階調ランプ・影色・リムライト・（必要なら）マットキャップ）
- 輪郭線は inverted hull（法線方向に押し出した裏面描画）。生成メッシュは法線を平滑化してから使う
- ライトは平行光源 1 つ + 半球光のみ。影はシャドウマップ 1 枚。ライトを増やさない
- ポストプロセス: ブルーム（控えめ）・ビネット・色調補正。輪郭線のポスト処理（深度/法線エッジ）は
  inverted hull で不足する場合に追加
- アニメらしさは演出（剣筋トレイル・ヒットストップ・フラッシュ・カメラシェイク）で担保する

**理由**: 資産の出自（Tripo / VRoid / プリミティブ）に依らず見た目を統一する。

## ADR-010 キャラクター資産は Higgsfield コネクタ経由で自動生成する

**状態**: 採用（2026-10-03）。ADR-005 の手順部分を置き換え

**背景**: 人手の工程（画像生成→Tripo→リグ→Mixamo）が放置の最大要因になりうる。computer use・ブラウザ操作・
ChatGPT/Codex CLI は、このセッションからは使えない（PC 未接続、`chatgpt.com`/`api.openai.com` は遮断）。

**決定**: 画像生成（`gpt_image_2_5`）→ 3D 化（Tripo H3.1）→ リグ＋モーション（Meshy）を Higgsfield コネクタで実行し、
結果 GLB を CDN から取り込んで `tools/inspect-glb.mjs` で AI が検査する。詳細と費用は `docs/05-asset-automation.md`。
人間の関与は「デザインの採否」のみ。重要キャラの原案をユーザー自身が作る運用は引き続き可能（同じ経路に画像を渡す）。

**理由**: 仮キャラ 1 体で全工程を通し、約 17 クレジットで品質が許容範囲であることを確認した。

**代償**: 別サービスのクレジットを消費する（ユーザーの Tripo 手持ちクレジットは使わない）。Meshy のリグは
人型前提で、指・髪・服のボーンがなく、スキニングに破れが出る。非人型の敵は未検証。

**見直し条件**: M1 でスキニングの破れが許容できない場合、VRoid（VRM）経路か Tripo 直接 API の骨格に切り替える。

**一部置き換え（2026-10-03）**: **攻撃モーションの調達**は ADR-012 で手付け（キー → IK → 焼き込み）に変えた。待機・走り・回避・被弾・死亡は引き続きこの経路（Meshy ライブラリ）。

**追記（2026-10-03）**: 1 体目は実機で全動作が崩れた。`tools/skin-stress.mjs` で測ると辺の 11〜15% が 1.8 倍超に伸びており、
Meshy の返却直後でも同値 → 自動リグのウェイト破綻（裾の広い服が主因）。2 体目は本人の 3 面図から四角メッシュで生成し、
位置結合＋ウェイト平滑化＋接地補正を加えて 0.26〜1.1% まで下げて採用した。手順は `docs/05-asset-automation.md`。
以後、キャラ資産は**数値検査を通さずに採用しない**。

**追記（2026-10-03）— 輪郭線の弱点と対策**: 生成メッシュの細い溝（背骨・脇）や裾では、inverted hull の押し出しが表面を突き破り、
暗いギザギザの線になる（腰の背面で実機の指摘。輪郭線を消すと消えることで切り分けた）。対策は 3 つ。
(1) 押し出し専用に平滑化した法線 `aONormal`、(2) 凹み量による輪郭線の削減 `aOutlineCut`（`src/render/outline-attrs.ts`。UV の継ぎ目で複製された頂点は同じ値にする）、
(3) 輪郭線を視線方向に 6mm 奥へ送る `uDepthPush`。外周の輪郭は手前に何もないので影響しない。キャラ以外のメッシュは属性が無く、従来どおり満額の輪郭線になる。

**追記（2026-10-03）— 顔の輪郭線**: 輪郭線の太さは画面上で一定（距離に比例して押し出す）ので、ゲームのカメラ距離（約 5m）では目鼻・唇・前髪の筋より輪郭線のほうが太くなり、
横顔が黒い塊になる（実機の指摘「横顔の違和感」。輪郭線を消すと目・鼻・唇・耳がはっきり見えることで切り分けた）。顔（頭ボーンに乗る頂点）の太さ倍率を 0.35 → 0.04 に下げた
（0.12 でも黒い筋が残り、0.04 でほぼ消える。`src/character/loader.ts` の `faceOutlineScale`）。髪の外周の輪郭線は細く残る。

## ADR-011 ポスト処理を 2 工程に減らし、解像度を負荷に応じて自動調整する

**状態**: 採用（2026-10-03）。ADR-009 のポスト処理の「構成」だけを置き換える（ブルーム・ビネット・色調補正という方針は変わらない）

**背景**: iPad 実機の計測（`?perf=1`）で、fps が描画解像度に比例して落ち、ポストの構成が大きな割合を占めていた。
EffectComposer の構成は「シーン → ブルームを MSAA ターゲットへ加算 → グレードをもう 1 枚の MSAA ターゲットへ → 出力」で、
画面サイズ・HalfFloat・MSAA 4× のパスを 3 回通し、そのたびに深度も含めて解決（resolve）していた。

**決定**:
- ポストは `src/render/post.ts` に自前で持ち、「シーン（MSAA 4×・HalfFloat・深度は解決しない）→ ブルーム（半解像度のミップ鎖）→
  最終 1 パス（ブルーム加算 + 色調 + ビネット + フラッシュ + sRGB 出力、画面へ直接）」の 2 工程にする。
  ブルームの式・ミップ構成・色調の式は旧構成（UnrealBloomPass / 旧 GradeShader / OutputPass）と同じ。EffectComposer は使わない。
- 描画解像度は動的に調整する（`src/render/adaptive-resolution.ts`、純粋ロジックで vitest 済み）。段は pixelRatio 1.5 → 1.25 → 1.0
  （デバイスの DPR を超える段は潰す）。実フレーム間隔の 60 フレーム平均が 21ms を超えたら 1 段下げ、17.6ms 以下が 6 窓（約 6 秒）続いたら 1 段戻す。
  戻して失敗した段は次に戻すまでの待ちを倍にして振動を防ぐ。起動直後と段の切り替え直後は捨てる。
- URL: `?dpr=1.25` で解像度を固定、`?adaptive=0` で動的調整だけ止める（スクリーンショット・計測用。`npm run shot` は止めて撮る）。

**試して捨てた案**: シーンを RGBA8（sRGB 格納）にして帯域を半分にする案。クリスタルなどの発光物は 1.0 を超える値でブルームを出しており、
LDR に潰すとブルームがほぼ消えた（旧構成との画像比較で確認）。HDR のまま保つ。R11G11B10（HDR で 4 byte/px）は端末対応が要るので、
既定にはせず `?perf=1` の計測行に入れてある。

**検証**: 旧構成と同じ決定的なフレームで画像比較し、背景・ブルーム・色調は差が 2/255 以内（キャラの輪郭の縁は実行ごとの揺れと同程度）。
ヘッドレス（SwiftShader）でポスト分の時間が約 33% 減（CPU ラスタライザなので実機の値ではない）。実機の fps は本人が再計測する。

**代償**: ポストを自前で保守する（パスは 2 + ブルーム 11 回で単純）。最小段 1.0 では画面がやや甘く見える場面がありうる（2388×1668 の画面に対し 1194×834 相当）。

**見直し条件**: 実機の再計測で 60 fps に届かない場合、`?perf=1` の行（ブルーム 1/4 解像度・MSAA 切・R11G11B10・影・輪郭線）を見て次の手を選ぶ。

## ADR-012 攻撃モーションは手付け（キー → IK → 焼き込み）で作る

**状態**: 採用（2026-10-03）。ADR-010 の「攻撃モーションを Meshy ライブラリから取る」部分を置き換える。1 段目（combo1）から始め、2・3 段目、重撃・回避へ広げる。

**背景**: 実機で「攻撃モーションはやはりまだ違和感が大きい」。Meshy の斬りクリップは (1) 全身が振り回され重さが無い、(2) 区間を切り出してつなぐと段の境目でポーズが跳ぶ
（フェードで 70m/s の剣先になる）、(3) 腕の挙上が大きいと脇が破れる（129° 超）、(4) 片足が 1.6〜3.5cm 浮く、(5) 手の持ち方と剣の向きが合わない、という問題を持ち、
区間の選び直しやクロスフェードの調整では直せなかった。モーション自体を、こちらの狙いどおりに作れる必要がある。

**決定**: 攻撃のポーズを「**どこに剣があり、体がどう向き、足がどこにあるか**」で書き、腕と脚を IK で関節に直して 60fps の `AnimationClip` に焼く。
- `src/character/ik.ts`（2 ボーン IK・座標系・蝶番）/ `rig.ts`（骨の親子・基準ポーズ・蝶番軸・グリップの純粋なデータ）/ `pose-solver.ts`（1 フレーム分の意図 → 全ボーンの回転）/
  `authoring.ts`（キー列 → タイムライン → サンプル → 焼き込み）/ `rig-capture.ts`（読み込んだ GLB から Rig を作る）。データは `src/character/data/*.ts`（combo1.ts）。
- 体幹（腰・胸・頭）は idle の t=0 に対する差分回転（yaw / pitch / roll）。剣の位置は右肩からの極座標 [方位°, 仰角°, 距離] を**胸の座標系**で書く（胸をひねると腕と剣がいっしょに動く）。
  剣の向きは「刃の向き + 面の法線のヒント」。肘は pole（向かう方向）で決める。足は**ワールドに固定**した位置で書き、ルートが進んでも滑らない（届かなければ腰を下げる）。
- 基準ポーズは idle クリップの t=0（Meshy のバインドポーズは左右非対称で、そのまま使うと片腕が浮く）。肘・膝の蝶番軸は走りクリップの曲がったフレームから**実測**する
  （cross(上腕の向き, 前腕の向き) を骨のローカルへ戻して平均。実機の資産で腕のばらつき 0.003°、脚 0.7°。本当に蝶番として動いている）。
- 剣はグリップ（`HERO.sword`）から逆算して手首の位置と手の回転を決める。前腕のねじれは前腕と手首で半分ずつ。
- 前進（踏み込み）は authored の `rootZ` カーブに従い、`Player.stepAttack` が毎ステップの差分で動く。攻撃データ（`AttackDef.authored`）が持つのは当たりの時刻だけ。
- クリップは読込時に焼く（37 フレーム、ミリ秒）。Rig 外の骨（head_end など）は idle の姿勢の定数トラックで固定する（トラックが無いと再生のたびに元の状態へ戻る）。

**試して捨てた案**
- **ねじれの自動最適化を実行時に入れる**: 手首のねじれ・曲がりが最小になる剣の roll を毎フレーム探す案。刃の面が斬りの面から外れ（横腹で叩く）、局所解で roll が跳ぶ恐れがあるのでやめた。
  代わりにオフラインの探索（`tools/scratch/combo-opt.scratch.ts`、git 管理外）で候補を出し、キーに `roll`（度）として書く。
- **キー間をスプライン補間にする**: 速度の折れは 60fps の 6〜8 フレームの斬りでは見えない。ポーズ（キー）の質と最高速の位置のほうが効く。必要になったら足す。
- **手首の曲がりを骨の Y 軸で測る**: 手ボーンの Y 軸は指の向きから約 22° ずれているので、idle でも 33° と出る。`HERO.hand.right.f`（指の向き）で測る（idle 50° 基準）。

**検証（1 段目、実機の資産）**: ゲーム内で 3 方向 + 手元の近接を撮って確認（脇のささくれなし、手首の破綻なし）。上腕の最大挙上 104°（目安 130° 以下）、肘は伸び切りの手前（最小 11°）、
接地足の滑りは 0.0cm（初回は最大 3cm: アニメは攻撃開始の描画で 1 フレーム進むので、sim の前進を 1 フレーム先にそろえて解消）、剣先の最高速は体の前を通る瞬間でそこから減速（当初「約 25m/s」と書いたのは測り方の誤りで、剣先の実測は 119m/s だった。のち 85m/s に下げた。下の追記）。
手首のねじれは最大 127°（前腕と手首に半分ずつ）、曲がりは idle 基準から約 +50° で、見た目に破綻はないが、近接で見える段が出たら `roll` で詰める。

**代償**: ポーズを手で書く労力がかかる（1 段で 5〜6 キー）。指は動かない（Meshy のリグに指ボーンがない）ので、握りは固定。（2・3 段目は 2026-10-03 夜に手付けになった。下の追記）
**見直し条件**: 手付けの質が iPad 実機で「違和感が残る」と言われたら、キーの数・補間・グリップ角の可変（掌の中で剣を回す）を検討する。

**追記（2026-10-03 夜）: 2・3 段目も手付けにした／連鎖の仕組み（`continueFrom`）**
実機の指摘「1 段目はだいぶマシ。2 撃目以降は体の形が変形するなど課題が多い」。原因は、2・3 段目が Meshy の Left_Slash / Thrust_Slash のままで、1 段目の終わりの姿勢からクロスフェードしていたこと
（腰のひねり方が違うクリップ同士を混ぜると胴がねじれてつぶれる）。そこで 2 段目（combo2: 右逆袈裟）・3 段目（combo3: 右の突き）も手付けにし、Meshy の区間は撤去した。
- **`AuthoredAttack.continueFrom = { attack, t }`**: 前の技の時刻 t の姿勢から始める。t=0 のポーズ（体幹・剣・両手・足・腰の高さ）が前の技の時刻 t と一致するので、受付時点のつなぎ目で姿勢が跳ばない。
  キーの無いチャンネルは idle ではなく前の姿勢のまま保つ（`'idle'` と書けば本当の idle）。ルートは新しい攻撃の原点に付け替える（rootZ は 0 から。足の z は「前の足の位置 − 前のルートの前進量」＝世界での位置は変わらない）。
  `rootZCurve` は前の技に依存せず 0 から数える（sim が見た目と切り離して使える）。`attacks.test.ts` が「continueFrom が前の技のクリップと cancelAt を指す」ことを検査する。
- **受付中は姿勢を保つ**: 受付（cancelAt）から戻りの手前までは振り抜きの姿勢を保ち（combo1 は 0.37〜0.5、combo2 は 0.32〜0.45）、そのあとで idle に戻る。遅めに押してもつなぎ目が跳ばない。
  代償として単発の硬直が 0.07〜0.13 秒延びる（回避キャンセルは持続の後からできる）。保持のあとの押下（戻りの途中）は、フェード 0.05 秒で 2 段目の開始姿勢へ引き戻すので、右足が最大 7cm/フレーム動く（測定のみ。目立つなら戻りを短くする）。
- **斬りの速度**: 1 段目の剣先が 3 フレームで 2m 動いて（119m/s）コマ飛びに見えたので、斬りの区間を 0.055 → 0.075 秒に延ばして最高速を 85m/s（1 フレーム 1.4m）に下げた。2 段目も最高 81m/s。
- **手首のねじれが ±180° をまたがない**: 3 段目の突きは面の向きの取り方でねじれが 109° → 156° → −125° と折り返して、前腕の骨が 1〜2 フレームで反転しうる値になった。面を「平らな面が上」（`face: [0,1,0]`）にして 109° → −52° の連続な変化に収めた
  （ねじれは `swingTwist` で ±180° に折り返されるので、キー列の途中で 180° をまたぐと前腕が反転する。`combo-roll2` / `combo-diag` の表で確認する）。
- 診断値: 3 段とも腕・脚のクランプ 0、握りの誤差 1e-16 m、上腕の最大挙上 104° / 92° / 92°、手首のねじれ最大 128° / 126° / 109°、接地足の滑り 0.0cm（3 連続でも。3 段目の後ろ足は小さく浮かせて引き寄せる）。

**追記（2026-10-03 深夜）: 左手の置き場／重撃・回避も手付けにした**
実機の指摘「もう片方の手が手持ち無沙汰になっているのが気になる。何も持っていない場合は違和感のない手の形にして」「重と回避にも手をつけてみましょう」。
- **左手（素手）**: 指ボーンが無く手の形は変えられない（力を抜いて軽く握ったメッシュ）。形ではなく**置き場所で意味を持たせる**。腕をまっすぐ伸ばすと手が力なく垂れて見え、腹に当てると腹を押さえて見え、
  体の中心へ寄せると胸を抱えて見えたので、(1) 肘は必ず曲げる（距離は腕の長さ 0.487m の 0.8 倍以下）、(2) 手は体から離す、(3) 剣の動きと逆に動かす（引き手）、の 3 点を守る。
  共通のポーズを `src/character/data/offhand.ts` に置いた: 構え手（左肩の真正面・みぞおちの高さ、振りかぶりと溜め）/ 引き手（左腰の前、斬りに合わせて引く）/ 脇（左腰の横に垂らす、振り抜き後）。
  盾を持つ場合は同じ枠（左腕の置き場）を盾持ちのポーズに差し替える想定（`docs/06-moveset-ideas.md`）。
- **重撃（heavy）**: 縦斬り（斬りの面 tilt = 90°）。0 → 0.38 腰を落として体を反らせ剣を頭上へ（0.44 まで頂点で一拍）→ 0.51 に剣が前を水平に通る最高速（82m/s）→ 0.58 に前下で止まる。
  右足の大踏み込み（0.3 → 0.53、弧 0.16m）でルートが 0.5m 進み、左足は戻りで追いつく。全体 1.0 秒（60f）。剣先は止まった所で床に約 13cm 食い込む（叩きつけた見え方。気になれば角度を詰める）。
  診断値: クランプ 0、上腕の最大挙上 108°、手首のねじれ最大 85°、肘の最小曲がり 43°。
- **回避（dodge）**（**superseded by ADR-019**: 実機で崩れて見えたため、前転と後ろステップに作り直した）: 低く前傾して 2 歩で駆け抜けるダッシュ。剣は右腰の後ろに水平に寝かせる。0.04 → 0.46 で 3.1m（最高 10m/s。旧 Meshy の前転は初速 9.5m/s・3.6m）。右足を振り出して 0.2 に着き、0.15 に蹴った左足が 0.34 に前へ着く（0.15〜0.2 と 0.3〜0.34 は両足が浮く）。全体 0.58 秒（35f）。
  最初の版は足の運びと腰の沈みを間違え、腰が地面すれすれの滑り込みに見えた。原因は「後ろ足が腰から 0.95m 後ろに残った」ことで、**蹴り足は腰から約 0.5m 後ろになった時点（ルートの進みから逆算）で離す**ように直した。
  診断値: クランプ 0、上腕の最大挙上 38°、手首のねじれ最大 112°。
- **回避の前進も rootZ に従う**: これまで回避の前進は初速 9.5m/s・減衰の定数（`DODGE.speed`）だったが、手付けのクリップと一致しないと足が滑るので、`DODGE.clip`（= `DODGE_CLIP`）の rootZ カーブを使い、
  `Player.stepDodge` が攻撃と同じ 1 フレーム先にそろえた差分で進む。無敵は 3〜20f（0.05〜0.33 秒、飛び出しから着地まで）、攻撃へのキャンセルは 26f 以降（立ち上がりの手前）。
  Meshy の `heavy` / `dodge` の区間と `HERO.dodge.rate` は撤去した。`attacks.test.ts` に重撃と回避の検査（前進の単調性・最高速・無敵とキャンセルの順序）を足した。
- **重撃の入力は暫定**: 専用の「重」ボタン（`InputIntent.heavyPressed`、キーボードは H）を置いた。コマンド構成の決定（`docs/06-moveset-ideas.md`）まで、実機で動きを確認するための仮。
- 実機（ゲーム内）の接地足の最大の動き: 重撃 0.9cm/フレーム、回避 1.6cm/フレーム、3 連コンボ 1.9cm/フレーム（いずれも着地・離地の 1〜2 フレームのみ）。


**追記（2026-10-04）: 踏み込み（ステップイン）を強めた**
実機の指摘「踏み込みが足りない？のが違和感かもしれない。よくある 3D アクションゲームのモーションを参考にしてみて欲しい」。
- **測定（改修前）**: 着地の瞬間の前足は腰（ルート）より 1 段目で 0.12m 前、2・3 段目は腰の真下かそれ以下。足の幅は 0.5m 以下、腰の沈みは 5〜7cm、ルートの前進は 0.3m（重撃 0.5m）。
  足は「ルートといっしょに運ばれる」だけで、**前へ踏み出して体重を乗せる**動きになっていなかった。2・3 段目は右足が剣の通過（0.15s）より遅れて 0.23s に着く（着地より先に斬っていた）。
- **参考にした作り**: 軽い攻撃は 0.4〜0.8 秒・予備動作 0.1〜0.2 秒で、ルートモーションで 0.5〜1m 前進して間合いを詰める。力は足 → 腰 → 胸 → 腕 → 剣の順に伝わる。
  斬りの当たる瞬間に足を着き、体はそこで止まって振り抜きの余韻が残る。フェンシングのランジは前足が 0.3m 前へ出て、最終の足の幅が腕の長さの約 2 倍（約 1.45m）になり、
  力は「腕の伸び → 腰の前進 → 膝がつま先の上 → 後ろ足の回転」の順に出る。出典: [Sword melee animation guide](https://mocaponline.com/blogs/mocap-news/sword-melee-animation-guide) /
  [Combat animation game dev guide](https://mocaponline.com/blogs/mocap-news/combat-animation-game-dev-guide) / [Anatomy of an enemy attack in Dark Souls 3](https://www.gamedeveloper.com/game-platforms/anatomy-of-an-enemy-attack-in-dark-souls-3) /
  [Max your lunge (Guy Windsor)](https://www.guywindsor.net/wp-content/uploads/2013/03/Max-Your-Lunge-2007.pdf) / [Pixelblog 9: melee attacks](https://slynyrd.com/blog/2018/9/8/pixelblog-9-melee-attacks)。
- **作り直し（combo1〜3・重撃）**: 次の 7 つを守る。
  1. **足は腰の前後へ開いて着地**する: 前足は腰の 0.3〜0.4m 前、後ろ足は 0.3〜0.4m 後ろ（幅 0.5〜0.8m）。
  2. **ルートは着地まで加速し、着地で減速**する（`in` → `out` の 2 区間で、加速と減速の最高速を揃える。1 段目は約 4.1m/s）。着地のあとも腰が前足の上まで流れる。
  3. **着地は剣の最高速の直前**（1 段目 0.235 → 0.245、2 段目 0.16 → 0.17、3 段目 0.17 → 0.18、重撃 0.5 → 0.51）。
  4. **着地で腰が沈み、体が前へ倒れる**（腰 −0.14〜−0.2m、胸の前傾 10〜24°）。予備動作でも腰を少し沈めて後ろ足に体重を乗せる。
  5. **後ろ足は床を滑らせず、小さく浮かせて引きつける**（空中で最大 10m/s ほど。接地中の滑りは 0）。足が前へ出る間もルートが先行して、足が腰から 0.5m 以上離れて腰が自動で下がることがない。
  6. **腰 → 胸 → 腕・剣の時間差**（`src/character/data/stagger.ts` の `pose()`。腰の回転を 0.03 秒、胸と頭を 0.015 秒だけ早く完了させる。腰の沈みと前傾、足は基準の時刻）。
     全部が同時に動くと体が一枚の板のように回る。
  7. **受付（cancelAt）から先はルートを止める**。遅めに押しても、次の技の原点と見た目がずれない（`attacks.test.ts` が検査）。
- **数値**: 着地の瞬間の前足の位置（腰から）/ 後ろ足 / 幅 / ルートの前進（着地まで → 終端）:
  1 段目 +0.39 / −0.34 / 0.73 / 0.30 → 0.57m（旧 +0.12 / −0.38 / 0.50 / 0.3m）。2 段目 +0.27 / −0.26 / 0.53 / 0.34 → 0.58m（旧 0.00 / −0.17 / 0.17 / 0.3m）。
  3 段目（突き。ランジ）+0.39 / −0.42 / 0.81 / 0.34 → 0.60m（旧 +0.01 / −0.41 / 0.42 / 0.3m）。重撃 +0.37 / −0.37 / 0.74 / 0.48 → 0.81m（旧 −0.01 / −0.40 / 0.39 / 0.5m）。
  3 連の総移動はおよそ 1.7m、重撃は 0.81m。足を空中で運ぶ速さは最高 6〜10m/s（走りの足の速さ）。腕・脚のクランプ 0、腰の自動補正（足が届かず腰を下げた量）は重撃の着地直前（0.45〜0.48s）の最大 0.05m だけ（沈みを前倒しする向きなのでそのまま使う）で、ほかは 0。
  剣先の最高速は 1 段目 89m/s（0.233s）・2 段目 67m/s・重撃 84m/s。
- **足を手で書くときの計算**: 足首の腰（ルート）からの前後位置 A = 「idle の足首 − 腰」（左 +0.136 / 右 −0.094）+ 足の z − ルートの前進 − 腰の z（前傾）。
  脚の長さは約 0.75m なので、腰の高さが 0.17m 下がっていれば前足は +0.5m まで、後ろ足は −0.45m まで届く（届かないと腰が自動で下がる）。
  戻りで idle に揃う条件は「最後に残る足の z = ルートの前進」。2・3 段目は着地した右足が idle では後ろの足なので、戻りで左足が前へ出て右足が少し引く。
- **代償・調整**: 連続コンボで大きく進む（総 1.7m）。進みすぎ・足りないは、各ファイルのルートと足の z（着地の位置）を同じ率で増減すると、つなぎ目を保ったまま変えられる。足の運びが速すぎて見えるなら、剣の通過を 0.02 秒遅らせる。
  後ろ足のかかとを上げる（`pitch` + `lift`）のは未実装（足は平らなまま）。**実機で未確認**。

## ADR-013 コマンド構成は「攻撃 / 回避 / ガード」の 3 つにする（案 A）

**状態**: 採用（2026-10-04）。**実装は M3 の後**（`CLAUDE.md` の最優先原則: デモ完成まで武器・技・防御などの新システムには着手しない）。

**背景**: 「少ないコマンド数（最大でも 3 種程度）で色々な剣のモーションのバリエーションを」という指示に対し、`docs/06-moveset-ideas.md` に 3 案を出した
（A: 攻撃 / 回避 / ガード、B: 弱 / 強 / 回避、C: 攻撃 / 回避 / 特技）。2026-10-04 に本人が **案 A** を選んだ。
iPad は両親指で、画面の右下にすでに攻撃・回避・LOCK（と確認用の「重」）が並ぶ。ボタンを増やさず、入力の種類・スティック方向・直前の行動で技を出し分ける案 A が、
指の置き場と作る本数（技 1 本は手付けで数時間）の両方に合う。盾（左手）の役割がそのままガードボタンになり、左手の件（盾か素手か）とも噛み合う。

**決定**
- ボタンは **攻撃 / 回避 / ガード** の 3 つ。技は次の軸で出し分ける: 攻撃のタップ / 長押し、スティック方向（押した瞬間）、コンボの位置、直前の行動（回避直後など）。
- **重撃は攻撃の長押し**。押した瞬間は軽攻撃の予備動作に入り、まだ押していれば頭上の構えで止まり、離すと振り下ろす（押下時間を待ってから軽攻撃を始めると全攻撃が遅れるので）。
- **ガード**は左手の役割。盾あり: 保持で構え、敵の攻撃の直前のタップで弾く（パリィ）。盾なし: 剣を体の前に立てて受ける。盾は拡張フェーズ。
- 作る順番（M3 の後）: ① 回避直後のダッシュ斬り（`continueFrom` で安く作れる）② スティック方向の 1 撃目（前突き / 後ろ払い / 横薙ぎ）③ 長押しの溜め → 重撃 ④ ガード / パリィ ⑤ ジャスト回避の反撃。
- 数の目安は、攻撃 8〜10 技・ガード側 2〜3 技・反撃 1〜2 技（ボタンは 3 つのまま 13 技前後）。

**いまのコード（暫定のまま）**: 専用の「重」ボタン（`InputIntent.heavyPressed`、キーボードは H）は残す。上の ③ で長押しに置き換えるときに外す。ガードのボタンはまだ無い。
**→ 更新（2026-10-04、ADR-018）**: ①②③ を実装し、「重」ボタン（`heavyPressed`）は廃止して長押し（`attackHeld`）に置き換えた。ガード（④）は M4-2。

**未決**: 盾を標準にするか、素手を標準にして盾は装備で出すか（`docs/06-moveset-ideas.md` §4・§6）。ガードを入れる M3 の後に決める。
**→ 決定（2026-10-04、ADR-020）**: **素手を標準にして、盾は装備で出す**。ガード（④）は M4-2 で実装した。

**代償**: 長押しとスティック方向に技が隠れるので、操作の発見しやすさ（チュートリアル表示）が要る。ガードが入るまで、左手は構え・引き手・脇に置くだけ（`offhand.ts`）。
**見直し条件**: 実機で長押しの判定がもたつく、またはスティック方向の技を誤爆するなら、案 B（強ボタン）の追加を検討する。

## ADR-014 ヒット判定は「攻撃者に付く前方の領域 × 敵の円」で行い、剣先の軌跡では判定しない

**状態**: 採用（2026-10-04）。ADR-003（XZ 平面のカプセル衝突）・ADR-004（フレームデータ駆動）の具体化。

**背景**: M2 の最初に「当たり」を作る。攻撃の剣先は手付けクリップで最高 85〜119m/s（1 フレーム 1.4〜2m）で動くので、
フレームごとの剣先の位置（または前フレームとの線分）で判定すると、相手の円（半径 0.5m）をすり抜ける・当たる時刻が演出と合わない。
物理エンジンを使わない方針（ADR-003）では、剣のボーンに追従する当たり判定のコライダーも持たない。

**決定**
- 攻撃側のヒットボックスは **攻撃者の XZ 位置と向きに付く領域**。形は 2 種類: `arc`（扇形。斬り。届く距離 `range` は相手の円の縁まで、`halfAngle` は片側の角度）と
  `line`（線分に幅。突き。`length` と `radius`）。相手の円の大きさぶんは判定に含める（扇の角度は円の見かけの広がりだけ広がる）。
- 領域は **持続フレーム（`activeStart`〜`activeEnd`）のあいだ毎 sim ステップ評価する**。攻撃者がルートモーションで進めば領域も一緒に進む。剣先の最高速とは無関係なので、すり抜けない。
- 被弾側（ハートボックス）は XZ の円（`Hurtbox` = 円 + id + 無敵フラグ）。高さ（Y）は見ない。
- **1 攻撃 1 対象 1 回**は `HitTracker`（対象 id の集合）。攻撃を始めるたびに `reset()` する（コンボの次段は新しい攻撃なので、同じ敵にまた当たる）。
  無敵の対象には当てず、記録もしない（無敵が切れたあと、持続が残っていれば当たる）。
- 持続の判定は「攻撃を始めてからの sim フレーム f が `startup ≤ f < startup + active`」。`Player.step()` の後に読むと、f は描画されている姿勢のアニメ時刻 f/60 に一致する。
- ダメージ・ヒットストップ・ノックバックは攻撃データ（`src/combat/data/attacks.ts`）、敵の HP・半径・ひるみ・ノックバックの掛け方は `src/ai/data/enemies.ts`。
- ノックバックは「指定の距離を指定のフレームで進んで止まる」（`Knockback`。線形に減速し、総移動量が距離ちょうどになる）。
- 命中の結果は `HitEvent`（ダメージ・ノックバック・ヒットストップ・方向・命中位置）。演出（ヒットストップ・フラッシュ・シェイク・数字）はこれを受け取る側が起こす。

**理由**: 当たる範囲を「技の見た目（振りの弧・突きの線）に合わせたデータ」として 1 か所で調整できる。純粋関数なので vitest で境界（縁・角度の継ぎ目・無敵・重複）を検査できる。

**代償**: 剣先が実際に通った所でなく「前方の扇」で当たるので、剣が敵の横を通っても扇の中なら当たる。見た目と当たりのずれは、`hitbox` の数値と持続フレームで合わせる。
高さの違う敵（空中・伏せ）は扱えない。

**見直し条件**: 大きな敵の部位ごとの当たり（頭だけ・弱点）、空中の敵、飛び道具が必要になったら、ハートボックスを複数の円/カプセルにする、または Y を含める。

## ADR-015 敵は FSM + 予備動作 + スーパーアーマー、プレイヤーは被弾後に無敵

**状態**: 採用（2026-10-04）。ADR-014 の続き（M2 の敵の攻撃・被弾）。

**背景**: 最初の敵（子鬼）を作ると、弱攻撃を連打するだけで敵が一度も攻撃できなかった（ボットで測定: 2.7 秒で撃破、被弾 0）。
敵は命中のたびにひるみ（22f）に入り、プレイヤーのコンボの受付間隔（20〜22f）と同じ長さなので、連続ひるみで完封される。
これでは予備動作（テレグラフ）も回避の無敵フレームも意味を持たない。

**決定**
- 敵の状態: `idle`（出現直後の待ち）→ `chase` → `windup`（予備動作 38f）→ `attack`（startup 3f + 判定 6f + 硬直 42f）→ `chase`、`hit`、`dead`。数値は `src/ai/data/enemies.ts`。
  予備動作の前半 22f はプレイヤーを向き続け、後半は向きを固定する（横へ動けば当たらない）。攻撃は判定の間前へ踏み込む。硬直のあと 40f は次の予備動作に入れない。
- **スーパーアーマー**: 予備動作の 16f 目から攻撃が終わるまで、ダメージが `armorBreakDamage`（30）未満の攻撃ではひるまない（ダメージは通り、ノックバックは 0.2 倍、フラッシュは出る）。
  重撃（34）は割り込める。前半（〜16f）は弱攻撃でも中断される。HP が 0 になる攻撃では倒れる。これで「攻撃を続けるか、避けるか、重撃で割るか」の選択ができる。
- 敵の攻撃の判定はプレイヤーの攻撃と同じ（ADR-014: 扇形/線分 × 円、1 攻撃 1 対象 1 回、無敵は当たらず記録もしない）。同じフレームに当たり合うなら、先にプレイヤーの攻撃を解決する（相打ちはプレイヤー優先）。
- プレイヤーは被弾すると `hit`（24f の操作不能）に入り、攻撃・回避は中断（先行入力も消える）、攻撃してきた側を向いて押される。**被弾後 56f は無敵**（ひるみの 24f を含む。連続被弾で即死しない）。
  HP が 0 なら `dead`（死亡クリップ）。無敵は回避の [3, 20]f、被弾後、死亡後の 3 つで、判定は `Player.body.invulnerable` に集約する。
- ヒットストップは sim だけを止める（`FixedStepper.timeScale = 0`）。止める長さは sim フレームで指定し、実時間（描画の dt）で数える。カメラ・エフェクト・UI は止めない（ADR-004）。

**暫定**: 全滅後の再スポーン（2.5 秒）、倒れてからの最初からのやり直し（3 秒）、頭上の HP バーは、M3 のリザルト・再戦・ロックオン HUD ができるまでの暫定。

**代償**: スーパーアーマーのせいで、弱攻撃のコンボは敵の予備動作の後半では止められない。ボットの目安は、連打のみ 3.6 秒で撃破・被弾 1 回、棒立ちは 20 秒で倒れる。
数値（HP・予備動作の長さ・アーマーの開始・無敵時間）は実機で見て調整する。
**見直し条件**: 敵が複数になったら、同時に予備動作に入る数の制限（攻撃権トークン）と敵同士の押し合いを足す。

## ADR-016 ロックオンとウェーブ戦闘・リザルト（M3）

**状態**: 採用（2026-10-04）。ADR-014・015 の続き。

**ロックオン**（`src/combat/lockon.ts`・`lockon-state.ts`、数値は `src/combat/data/lockon.ts`）
- ロックボタン: ロック中なら解除、そうでなければ **「画面の正面寄りの最寄り」** をロック（点数 = 距離 ×（1 + 0.7 × 正面からのずれ / π）。16m 以内）。対象がいなければ何も起きない。
- 切替: ロック中に右半分の **横スワイプ**（90px。1 回のドラッグで 1 回）、キーボードは Q / E。いまの対象から見て右（左）に最も近い角度の敵へ移る。その向きに敵がいなければ今のまま。連続しないよう 14f の間隔を空ける。
- 対象が倒れたら **残りの敵へ自動で移る**（いなければ解除）。22m を超えて離れたら解除。プレイヤーが倒れたら解除。
- カメラ（`ThirdPersonCamera.stepLock`）: sim で yaw を対象の方へ減衰補間する（ヨーの入力は使わない。ピッチは使える）。描画では注視点を対象へ 30% 寄せ、離れた敵が映る分だけ距離を引く（最大 2.5m）。ロックを解くとその向きのまま通常の操作に戻る。
- プレイヤー（`Player.setAim`）: 照準があれば、攻撃は対象の方を向いて始まり、立ち止まっているときも対象の方を向く。走るときはスティックの向き、回避はスティック方向（無入力なら向いている方の後ろ）。
- 見た目: 対象の胸に四隅の枠（ロックの瞬間に絞り込む）、画面上部に対象の名前と HP バー（頭上のバーはロック対象には出さない）、LOCK ボタンの点灯。

**ウェーブ戦闘**（`src/game/encounter.ts`、数値は `src/ai/data/encounters.ts`）
- デモの構成は 2 体 → 3 体の 2 ウェーブ。全滅させて 100f 後に次のウェーブ、最後を全滅させて 75f 後に勝ち。プレイヤーが倒れて 150f 後に負け（同時なら負け）。敵は「プレイヤーから見てアリーナの中心の向こう側」に、左右に散らして出る。
- **攻撃権**（`src/ai/swarm.ts`）: 同時に予備動作〜攻撃に入れる敵は 2 体まで。残りは攻撃の距離で構えて待つ。敵どうしは押し合って重ならない。
- 最後の 1 体を倒した瞬間と、プレイヤーが倒れた瞬間は **スローモーション**（`HitStop.slow`。0.3 倍 0.9 秒 / 0.35 倍 1.2 秒）。
- **リザルト**: VICTORY（撃破数・タイム・被ダメージ・被弾回数・S〜C のランク。ランクは時間と被ダメージの両方で決まる）/ DEFEAT。「もう一度」で最初から。連打の指で一瞬で再戦しないよう、出て 1.1 秒は押せない。リザルトの間は操作を受け付けない。暫定だった自動の再スポーン・やり直しは廃止した。

**代償**: ロック中はカメラを自由に回せない（ピッチのみ）。スワイプでの切替は、通常のカメラ操作と同じ領域なので、ロックしていないときの大きな横ドラッグでも「切替の入力」は出る（ゲームはロック中だけ使うので害はない）。
ボットで測った目安（2 ウェーブ・5 体）は、連打のみが約 19 秒でクリア・ランク A（被ダメージ 60）、回避を混ぜると被弾が減って S も出る、棒立ちは約 23 秒で敗北。数値は実機で見て調整する。
**見直し条件**: 敵が大きく増える・種類が増えるなら、攻撃権を敵ごとの重みづけにする。ロックの切替が誤爆するなら、スワイプのしきい値を上げる、または専用の切替ボタンを置く。

## ADR-017 効果音は WebAudio で合成する（音声ファイルを持たない）

**状態**: 採用（2026-10-04）

**背景**: M3 の完成定義に効果音（攻撃・命中・被弾・敵撃破）がある。音声資産の調達・ライセンス・容量・読込の手間を、個人用のデモのためにかけたくない。

**決定**
- 音はすべて **WebAudio のノイズと発振器の重ね合わせ** で合成する。レシピは `src/audio/data/sfx.ts`（層ごとに: 種類、周波数の from → to、フィルタ、attack、長さ、音量、遅れ）。外部依存も資産も増えない。
- 再生は `src/audio/sfx.ts`（レシピ → ノード。同時発音数 24 の上限、距離による音量、雑音は毎回違う位置から）。出力は `src/platform/audio.ts` の `AudioBus`（マスター → コンプレッサ → 出力）。
- **iOS Safari の作法は `src/platform/audio.ts` に集約**: AudioContext は開始画面のタップ **のイベントの中で** 作って resume し、無音のバッファを 1 つ鳴らす（`Hud.waitForStart(onTap)` が同期で呼ぶ）。
  止まっていれば以降のタップで再開を試す（電話・スリープからの復帰）。非表示で suspend。操作なしで始める `?autostart=1` や解放前は黙って何もしない。`?mute=1` で消せる。
- 鳴らす場面: プレイヤーの振り 4 種（当たりの 0.07 秒前に）・回避、命中（軽・重）・撃破、被弾、敵の予備動作の合図と振り（距離で音量）、ロック・切替・解除、ウェーブ、勝ち・負け、UI。
- 検証: `node tools/sfx-check.mjs`（`npm run build` のあと）が全音を OfflineAudioContext で書き出し、ピーク・実効値・長さ・終わりの静けさ（尻切れのプチ音）・直流成分を数値で検査し、`artifacts/audio/*.wav` を出す。`Sfx` は偽の AudioContext で vitest する。

**代償・既知の問題**: **耳での確認はしていない**（数値で「壊れていない・音量がそろっている」まで）。質感・音程・うるささは実機で聴いて、レシピの数値を直す。
iPad の無音スイッチ（消音）で WebAudio が鳴らない端末がある（ブラウザの仕様）。合成音なのでリアルな斬撃音ではなく、アニメ調の効果音の域。
**見直し条件**: 合成音の質感に満足できないなら、フリー素材などの音声ファイルを `public/assets/` に置き、同じ `SfxName` で差し替える（呼び出し側は変えずに済む）。

## ADR-018 コマンドの実装: 入力から技を選ぶ純粋関数と、攻撃の長押しの溜め

**状態**: 採用（2026-10-04、M4-1）。ADR-013（案 A）の実装。

**背景**: M3 でデモが完成し、拡張フェーズ（M4）の最初に「片手剣もコマンドの組み合わせで技を増やす」を入れる。ADR-013 で決めた案 A（攻撃 / 回避 / ガード の 3 ボタン）のうち、
攻撃側（タップ・長押し・スティック方向・回避直後）をここで作る。のちの盾（M4-2）・大剣（M4-3）が同じ仕組みを使えるよう、「どの入力でどの技か」と「技の数値」を分ける。

**決定**
- **技の選択は純粋関数**（`src/combat/moveset.ts`。vitest で検査）: 攻撃を押した瞬間の `stick`（none / forward / back / side）と `afterDodge`（roll / back / null）から技の id を返す。
  回避直後なら回避の種類のダッシュ技、そうでなければスティックで決まる。コンボの 2 段目以降（`AttackDef.next`）と溜めの放ちは通らない（Player が続きを管理する）。
- **スティックの読み方**: 大きさ 0.3 以上で「倒している」。ロックなしは常に「前」（攻撃は倒した向きを向いて始まるので、走りながらの攻撃 = 踏み込み）。
  ロック中は対象の向きから ±50° 以内が「前」、130° 以上が「後ろ」、その間が「横」。向きは対象のまま。数値は `src/combat/data/moveset.ts`。
- **技のセット（`SWORD_MOVESET`）**: なし = 弱攻撃 1 段目（→ 2 → 3）/ 前 = 踏み込み突き（`lunge`）/ 後ろ = 下がりながらの払い（`retreat`）/ 横 = 横薙ぎ（`sweep`）/
  ロール直後 = ダッシュ斬り（`dash`、逆袈裟の斬り上げ）/ 後ろステップ直後 = 踏み込み突き。回避が終わって 12f 以内、または回避のキャンセル可能フレーム以降に押すと「直後」。
- **重撃 = 攻撃の長押し**（「重」ボタンは廃止）: 押した瞬間は 1 段目の予備動作に入る（軽い攻撃が遅れない）。押し続けて 9f（0.15s、1 段目の斬りが始まる 0.17s の前）になったら溜め（`charge` 状態）へ移り、
  1 段目の予備動作の途中の姿勢から頭上の構え（`heavyCharge`、終端で止まる）になる。離すと構えが整ってから重撃（`heavy`、構えの終端から `continueFrom`）を放つ。
  構えが整って（18f）から 24f・54f 保持するごとに段階が上がり、威力が 1.0 → 1.25 → 1.6 倍（ダメージ・ノックバックの半分・ヒットストップ）。100f で自動で放つ。構えのあいだは動けず、向きだけロック対象へ向く。構えに入って 8f 以降は回避でキャンセルできる。
  剣が段階に応じて金色に光り、段階が上がる瞬間に閃いて合図の音が鳴る。
- **暴発の防止**: 長押しの判定は「この攻撃を始めたときに押していて、そこから一度も離していない」ときだけ（連打の指が触れたまま次の攻撃に入っても溜めない）。溜めに入れるのは 1 段目だけ（2 段目以降を押し続けても入らない）。
- 入力は `InputIntent.attackHeld`（ボタンを押している間 true）を追加し、`heavyPressed` を削除した。キーボードは J（長押しで溜め）。
- 数値（`ATTACKS` の lunge / dash / retreat / sweep / heavy、`CHARGES`）はすべて `src/combat/data/` にある。

**代償・既知の問題**: 長押しとスティック方向に技が隠れるので、操作の発見しやすさ（チュートリアル表示）が要る。技の手触り・長押しの速さ・スティック方向の誤爆は **実機で未確認**。
モーションは静止画の連続（`tools/motion-sheet.mjs`）と数値（`tools/motion-check.mjs`）で検査しただけで、動きの速さの感じは実機で見る。
**見直し条件**: 実機で長押しの判定がもたつく、またはスティック方向の技が誤爆するなら、ADR-013 のとおり案 B（強ボタン）の追加を検討する。
**追記（M4-3、ADR-021）**: 長押しの判定フレーム（`CHARGE_HOLD_FRAMES`）は溜めごとの値（`ChargeDef.holdFrames`。片手剣 9f / 大剣 12f）にした。クリップが 1 段目から続く時刻 × 60 と一致させる（テストで検査）。

## ADR-019 回避の作り直し: 前転（ロール）と後ろステップ、足の「腰基準」

**状態**: 採用（2026-10-04、M4-1）。ADR-012（手付け）の拡張。ADR-012 追記の「回避（2 歩のダッシュ）」を置き換える。

**背景**: 実機で「回避のモーションが崩れている」との指摘。モーションシートで側面から見ると、足が 1.5m 開く大股の飛び出しを 2 回繰り返し、剣は体の横へ針のように突き出ていて、
メッシュの変形ではなく **動きの設計そのもの**（回避というより大股のダッシュ）が崩れて見えていた。

**決定**
- 回避を 2 種類にする: **前転（ロール）** = スティックを倒していれば、その向きへ向きを変えて体を丸めて転がる（0.58s、前進 2.95m、無敵 3〜22f）/
  **後ろステップ** = 入力なし、またはロック中に対象から離れる向き（真後ろ ± 50°）へ倒したとき、向きを保って（対象を向いたまま）後ろへ跳ぶ（0.46s、後退 2.0m、無敵 2〜16f）。どちらも 26f / 22f 以降は攻撃でキャンセルできる。
- ポーズソルバに **足を腰の座標系で置く** 機能を足した（`FootTarget.rel`（0 = 世界に固定、1 = 腰に付く）と `lx/ly/lz`（腰の座標系の位置）、`knee`（膝の向きを腰の向きに追従させる））。
  ロール中は腰・胸・頭のピッチを 0 → 360° 回し、足は腰に付いて丸まって回り、着地で世界に固定し直す。後ろステップでは跳んでいるあいだ足が腰にぶら下がる。
  オーサリングの角度チャンネル（腰・胸・頭のヨー/ピッチ/ロール、足のヨー/ピッチ）は、`continueFrom` で姿勢を受け渡すときに ±180° を折り返して補間する（360° 回転の技のため）。
- ロールは「回転軸と平行に寝かせた剣」「逆さのとき腰を高く（頭が床に入らない）」「ルートの前進 ≒ 転がる球の周」の 3 点で成り立たせた。数値は `tools/motion-check.mjs` で床からの高さを骨単位で測って詰めた（頭の骨の最低 0.20m、剣先は床の上）。

**代償・既知の問題**: 見た目の確認は静止画の連続だけ。実機で見た「動きの速さ・距離・無敵のタイミング」は未確認。ロールの 0.58s は旧版（0.5s）より長い。
**見直し条件**: ロールが遅い・長いと感じるなら、`DODGE_CLIP` の時間と `DODGES.roll`（無敵・キャンセルのフレーム）を詰める。

## ADR-020 ガード・パリィ・盾: 素手が標準・盾は装備、構えは動けない、パリィで敵が崩れて反撃が通る

**状態**: 採用（2026-10-04、M4-2）。ADR-013（案 A）の ④ ガード / パリィの実装。ADR-013 の未決（盾を標準にするか素手を標準にするか）を決着する。

**背景**: M4-1 の実機確認のあと、本人の決定:「**素手を標準にして盾は装備で。2 系統ははっきりさせる**」（片手剣は左手が素手 / 盾、もう 1 系統は両手の大剣 = M4-3）。
ガードは左手の役割（ADR-013）なので、左手に何を持つかで構えの性能と動きが変わる。

**決定**
- **装備の組（ロードアウト。`src/combat/data/loadouts.ts`）**: `sword`（片手剣・素手。標準）/ `sword-shield`（片手剣 + 盾）。M4-3 で大剣（左手は塞がる）を足す。
  技のセット・溜め・ガード・走る速さ・クリップの版は装備で決まる（数値は attacks.ts / guard.ts / moveset.ts にあり、loadouts.ts は「どれを使うか」だけ）。
  **選び方**: 開始画面（チップ。選んだものは localStorage に保存、`?loadout=` で上書き）と、戦闘中の切替ボタン（右上。立っている・走っているあいだだけ。押すと次の装備へ）。
- **ガードは 3 つ目のボタン**（旧「重」の位置）。**押している間だけ構える**（`InputIntent.guardPressed` / `guardHeld`。キーボードは H、装備の切替は G）。
  - 構えは**その場から動けない**（向きだけ変えられる。ロック中は対象へ）。ADR-013 は「移動は遅くなる」としたが、手付けのクリップは全身を 1 つの姿勢で焼くので、歩きながらの構えは足が滑って崩れる（代償の節）。
  - 押した瞬間から構えに入る。先行入力は 12f（攻撃の持続が終わる・溜めの構え・回避のキャンセル可能フレームに入った時点で、押していれば構える）。
    構えに入って 4f 以降は攻撃・回避でキャンセルできる（弾いた直後の反撃はここから出る。スティックを倒していれば踏み込み突きなど、通常の技の選択）。
    構えは入って 8f までは解けず（連打でちらつかない）、解いてから 8〜12f は構え直せない（パリィの受付を開き続けられない）。
  - **盾**: 正面 ±80° の攻撃を 85% 軽減して受け止める（削りだけ通る。最低 1）、押されは 0.3 倍、受け止めた直後の硬直 12f。**構えに入ってから 10f（0.167s）はパリィ**。盾を持つと走る速さが 0.92 倍（盾の重さ）。
  - **素手**: 剣を体の前に斜めに構えて受ける。正面 ±60°、50% 軽減、押されは 0.6 倍、硬直 16f。パリィはない。
  - 構えの正面の外（横・背後）から来る攻撃は防げず、通常の被弾になる（構えは解ける）。
- **パリィ**（盾のみ）: 受付のあいだに敵の攻撃が当たると**弾く**。ダメージなし・押されなし・構えは保つ。敵は**体勢を崩す**（`stagger` 66f。予備動作・攻撃を中断し、スーパーアーマーは効かない。そのあと 30f は予備動作に入らない）。
  体勢を崩しているあいだに当てた攻撃は**反撃**: ダメージ 2 倍、ノックバック 0.5 倍（遠くへ飛ばさず、続けて当てられる）。崩れているあいだは何度当たっても崩れたまま（ひるみに上書きされない）。
- **盾の見た目**: 丸盾（`src/game/shield.ts`）を左前腕のボーンに付ける。面の向きは肘の蝶番軸から決める（曲げの外側 = 前腕を立てたとき前）。装備したときだけ表示。
  盾を持つ間は、攻撃・溜め・回避の手付けクリップを**左腕を盾の持ち位置に固定して焼き直した版**（`名前@shield`。`AuthoredSampler` の `leftHold`）で再生する（盾を構えたまま振る・転がる。体の左側に置くので剣の斬りが盾に当たらない）。
  待機も盾版（`idle@shield`。Meshy の待機は腕を下ろすので、盾の面が後ろを向いてしまう）。ガードの構え・受け・パリィは左腕を自分で決める手付けで、版は作らない。走りは Meshy のまま（腕と一緒に盾が振れる）。
- **演出**: パリィの受付のあいだ盾が水色に光る（弾けるタイミングが見える）、受け止め・弾いた瞬間に暖色の閃光、受け止めは小さなヒットストップと揺れ + 暖かい火花、パリィは強いヒットストップと揺れ + 水色の大きな火花 + 「PARRY」の文字。
  敵は体勢を崩すあいだ、のけぞって腕を振り上げ、水色に脈打つ。効果音は guard / parry / guardUp / equip を追加。リザルトに「パリィ」の回数（削りダメージは被ダメージに入れるが、被弾の回数には数えない）。
- 判定は純粋関数（`src/combat/guard.ts`: 向き・受付・軽減）と、`resolveEnemyAttacks` の防御の分岐（`Player.guardOutcome` → パリィ / ガード / 被弾）に分けた。Player は構えの状態機械、Enemy は `stagger`。

**代償・既知の問題**
- **構えは動けない**。複数の敵に囲まれると、正面の外からは防げない。歩きながらの構え（下半身は歩き・上半身は構え）は、クリップを部位ごとに重ねる仕組みが要るので拡張候補。
- **実機で未確認**: パリィの受付（10f）の難しさ、盾の軽減（85%）が強すぎないか、素手のガードの使いどころ、盾の重さ（走る速さ 0.92）との釣り合い、構えを解いたあとの待ち。数値はすべて `src/combat/data/guard.ts` / `loadouts.ts`。
- ガードできない攻撃（ガード破り）は未実装（敵が子鬼 1 種のため）。盾は 1 種（丸盾）。
- 盾版のクリップを起動時に焼く（全体で約 60ms@PC。クリップ数が倍になる）。大剣で左手が塞がるぶんも同じ仕組みで足せる。
**見直し条件**: パリィが難しすぎる・簡単すぎるなら parryFrames。ガードが強すぎるなら damageReduction と構えを解いたあとの待ち。歩きながら構えたいなら上半身の合成を検討する。
**追記（M4-3、ADR-021）**: パリィの数値は盾専用の `PARRY` から、**弾かれた敵の反応ごとのデータ**（`PARRY_EFFECTS`: `stagger` = 盾 / `down` = 大剣）に分け、`GuardDef.parryEffect` から引く形にした。盾の数値と挙動はそのまま。大剣のガード・パリィは ADR-021。

## ADR-021 大剣（両手持ち）: 左手が柄を握る、重く手数が少なく広い、パリィは盾よりシビアで弾かれた敵は倒れる

**状態**: 採用（2026-10-04、M4-3）。ADR-020 の 2 系統目（片手剣（素手 / 盾）と**両手の大剣**）。ADR-012（手付け）・ADR-018（コマンド）・ADR-020（ガード）の拡張。

**背景**: M4-2 の実機確認のあと、本人の指示:「盾はないが大剣でも盾よりシビアなパリィが可能。被パリィ時の敵の挙動も盾とは異なる。また、大剣は重く手数は少ないが高火力広範囲でこちらも色々なモーションが欲しい」。
大剣は盾を持てないので、**パリィの手段は剣そのもの**。盾の「受付が長くて安全に弾ける」と差をつけ、**狙って決めるぶん見返りを大きく**する。

**決定**
- **両手持ちの仕組み**（`AuthoredAttack.twoHanded`、`src/character/authoring.ts`）: 左手首の目標を、右手の握り（`grip`）と剣の向き（`blade`）から**毎フレーム導く**（右手の握りから石突き側へ `offset` = 0.24m）。
  手付けに左手（`left`）は書かず、左肘の向き（`leftPole`）だけ書ける（既定 `TWO_HAND_POLE`）。`continueFrom` の連鎖でも、前の技の導いた左手から続く。届かない姿勢は左腕のクランプとして `--stats` の armL に出る。
  **両手が柄に付くので、剣は胸の前から大きく外せない**（右肩 − 左肩は 0.24m、腕の長さは 0.44m。握りを右へ離すと左手が届かない）。大きな振りは**腰・胸のひねり**で作り、握りは胸の中心の近くを回す。
- **剣**（`src/game/greatsword.ts`）: 柄の中心（右手）から切っ先まで 1.62m、石突きは −0.4m（左手は下 0.24m）。右手のソケットに片手剣と一緒に付け、装備したほうだけ見せる。刃の光（溜め）・剣筋の帯は武器ごと。
  刃が長いので、腰・胸が前へ倒れていると前を向いた刃が下へ傾く（世界の仰角 ≒ 胸の座標の仰角 − 前傾）。**前傾の分だけ刃を上げて書き**、切っ先が床に刺さらないようにする（検査: 切っ先の最低 0.04m）。
- **手首のねじれ**: 大剣の刃は表裏が同じなので、`roll`（刃の軸まわり）は ±180° まで使える（片手剣は縁の向きがあり ±35°）。手付けの `roll` は **`?motionlab=1`**（ページ内で実リグに対して `AuthoredAttack` を焼いて統計を返す開発用フック。`src/debug/motion-lab.ts`）で、
  ねじれ・曲がりが小さく ±180° をまたがない組を探して決めた（実測: ねじれ ≤ 106°、曲がり ≤ 115°、腕・脚のクランプ 0）。
- **構え・待機・走り**: すべての技が構え（`GS_STANCE`: 剣を体の右前、腹の高さに、切っ先は前上がり）から始まり、構えへ戻る（`continueFrom`）。待機は構えの息づかい（`idle@greatsword`）、
  走りは **Meshy の走りの胴・脚のまま、腕のトラックだけを担ぎの姿勢で固定**（`overlayPose`。剣を体の右前に立てて持つ。走りは胴が前へ傾くので刃を立てて書く）。装備を替えたときは待機・走りのクリップを装備の版へ選び直す。
- **技のセット**（`GREATSWORD_MOVESET`。片手剣より予備動作が長く（約 0.3 秒）、ダメージ約 2 倍、範囲が広く、ヒットストップ・ノックバックが大きい。硬直も長い。数値は `src/combat/data/attacks.ts`）

  | 入力 | 技 | 動き | ダメージ | 範囲 |
  |---|---|---|---|---|
  | タップ | `gs1` | 右上 → 左下の袈裟斬り。左足を踏み込む（0.7m） | 22 | 扇 2.7m ±85° |
  | 1 段目の受付で再度 | `gs2` | 左下 → 右上の逆袈裟。**2 連で終わる**（手数が少ない） | 30 | 扇 2.8m ±90° |
  | 前 | `gsLunge` | 牛の構え（両手を頭の高さへ）から体ごと踏み込み（1.5m）、胸の高さへ貫く | 26 | 線 3.0m |
  | 後ろ（ロック中） | `gsRetreat` | 後ろへ 1.3m 跳びながら水平に薙ぎ払う | 18 | 扇 2.8m ±100° |
  | 横（ロック中） | `gsSpin` | 腰を沈めて跳び上がり、体ごと 1 回転して水平の円を描く（腰・胸のヨーを 360° 回す） | 30 | **円 2.7m（全方位）** |
  | ロール直後 | `gsDash` | 転がった低い姿勢から前へ 1.6m 跳び、真上から叩きつける | 34 | 扇 2.8m ±65° |
  | 後ろステップ直後 | `gsRise` | 低い姿勢から踏み込み、右下 → 左上へ斬り上げる | 24 | 扇 2.7m ±80° |
  | 長押し → 離す | `gsHeavy` | 頭上の構えから左足を大きく踏み込み（1.3m）、真上から叩き割る | 60 × 溜め | 扇 3.0m ±90° |

  子鬼のスーパーアーマー（`armorBreakDamage` 30）を割れるのは `gs2`・`gsSpin`・`gsDash`・`gsHeavy`。ヒットストップは 1 発 24f を上限（`HIT_FEEDBACK.maxHitStop`。溜めの倍率後）、ダメージ 20 以上は「強」の見た目（数字が大きく黄色）。効果音は大剣用に低く長い風切り 8 種。
- **溜め**（`CHARGES.greatsword`）: 12f（0.2 秒）押し続けると頭上の構え（1 段目の予備動作の途中。左足が床を離す前なので足を置き直さない）。構えが整ってから 30f・66f で段階が上がり、威力 ×1.3・×1.8（片手剣は ×1.25・×1.6）。最大 120f。
- **ロール・後ろステップ**: 片手剣のロールからルート・足・腰と胸の動きを引き継ぎ、**腕だけ作り直す**（`dodge@greatsword` / `dodgeBack@greatsword`。ルートの前進・長さは同じなので、sim の移動・無敵と見た目がずれない）。ロール直後 = `gsDash`、後ろステップ直後 = `gsRise` はこの版の受付の姿勢から続く。
- **ガード（盾なしでもパリィ）**（`GUARDS.greatsword`）: 両手で剣を体の前に立てて受ける。**パリィの受付は構えに入ってから 6f（0.1 秒）**（盾は 10f）。構えの動きそのものが「弾き」で、早すぎても遅すぎても弾けない。
  受け止めるだけのときの軽減は 65%（盾 85%・素手 50%）、正面 ±70°、押されは 0.5 倍、受けた硬直 14f、構え直しの待ち 14f（盾 12f）。**失敗すると痛い**。走る速さは 0.88 倍。
- **パリィの効果の種類**（`PARRY_EFFECTS`）: 弾かれた敵の反応を構えごとのデータにした（`GuardDef.parryEffect`）。

  | | `stagger`（盾） | `down`（大剣） |
  |---|---|---|
  | 敵の反応 | その場でのけぞって体勢を崩す（立ったまま） | **弾き飛ばされて倒れ**、寝て、起き上がる |
  | 押される距離 | 0.7m | **2.6m**（22f かけて滑る） |
  | 動けない時間 | 66f（1.1 秒） | **112f（1.9 秒）**、そのあと 50f は予備動作に入らない（盾は 30f） |
  | 反撃（ダメージ倍率 / ノックバック） | ×2 / ×0.5。**全期間** | **×2.4 / ×0.15**。倒れて起き上がる前まで（86f）。起き上がりの終わり（26f）は無防備だが倍率なし |
  | 演出 | ヒットストップ 9f、揺れ 0.05m、閃光 1.2、「PARRY」 | ヒットストップ 14f、揺れ 0.1m、閃光 1.7、「PARRY」（1.5 倍の大きさ）、重い効果音、倒れた音 |
  | 反撃の取り方 | 近距離のまま続けて当てられる | 遠くへ飛ぶので**踏み込みが要る**（突き・跳び叩きつけ・溜め斬りで届く）。1 撃が大きい（溜め斬りの反撃は子鬼を 1 撃で倒す） |

  敵は `down` 状態（`Enemy.parried(ev, effect)`）になり、`riposte`（反撃の倍率を持つ効果、受付のあいだだけ）を持つ。`resolvePlayerAttack` は `target.riposte` の倍率で反撃を計算する。見た目は後ろへ倒れて寝る（足元を軸に傾け、胴の太さぶん持ち上げる）→ 最後の 26f で起き上がる。
- **装備**: ロードアウト `greatsword`（表示名「大剣」。開始画面のチップ・切替ボタンは 3 つを順に回る）。左手が柄を握るので盾は持てない。

**代償・既知の問題**
- **実機で未確認**。確かめること: パリィの受付 6f の難しさ（狙って決められるか。厳しすぎないか）、倒れた敵への踏み込み（反撃に間に合うか）、大剣の重さの手触り（予備動作 0.3 秒・硬直・ヒットストップ）、各技の見た目と使い分け、走りの担ぎの見た目、ロールの見た目（剣を体の右へ水平に伸ばして転がる）。数値はすべて `src/combat/data/`。
- 左手は指ボーンが無いので、柄を握る形は作れない（位置だけ。手のメッシュは柄のそばに来る）。右手のソケットと左手のずれは目視で確認した範囲。走りの担ぎでは、左手が届く位置まで握りを上げてあるが、左腕はほぼ伸び切る（`gsCarry` の左腕のクランプは待機からの遷移の数フレームのみ）。
- `gsSpin` は全方位（半角 180°）。回転の見た目は 1 コマ 50〜70° で動くので、実機で目が追えるか見る。着地後は剣が体の右後ろに水平に残ったまま戻る（簡素）。
- 溜め斬りの切っ先は床すれすれ（0.04m）まで下りる（地面を叩く）。叩きつけの衝撃波・砂ぼこりは未実装。
- 敵が子鬼 1 種のため、`down` が使えない（倒れない）大きな敵・ガード破りの攻撃は未実装。
**見直し条件**: パリィが厳しすぎる・簡単すぎるなら `GUARDS.greatsword.parryFrames`（4〜8f の範囲）。倒れた敵への反撃が間に合わないなら `PARRY_EFFECTS.down` の距離・時間。大剣が強すぎる・弱すぎるなら技ごとのダメージ・硬直。

## ADR-022 リグの補正: 骨をメッシュの断面の中心へ寄せ、胴の重みを位置から作り直す

**状態**: 採用（2026-10-04、M4-4）。ADR-010（資産の自動生成）・ADR-012（手付け）の補強。`hero.glb` の骨と重みを加工する（メッシュ・テクスチャ・アニメーションの意味は変えない）。

**背景**: M4-3 の実機確認で本人の指摘:「操作感は問題ない。モデルがやはり崩れている。特に腰回り。一度根本的にモデルの関節やリグなどを見直した方が良いのでは？色々な動きに対応できるよう精巧化した方が近道ではないですか？」
これまでの腰の対処（輪郭線・テクスチャ。docs/05「腰の背面の崩れ」）は**静止時**の見た目で、ポーズ中の腰は未確認のままだった。再現して測ると、**リグそのものが原因**だった（本人の見立てのとおり）。

**診断**（`tools/motion-sheet.mjs --mode weights|wsum:…|ybands`、`tools/measure-joint-centers.mjs`、`tools/waist-stress.mjs`）
1. **骨がメッシュの中心から全体にずれていた。** メッシュは x = +4.2cm を軸に左右対称（胴・腕・脚の断面の中心が ±0.1cm で一致）なのに、骨盤・背骨は x = −3.6cm（**7.8cm 右へずれ**、右のウエストの縁から 1.7cm 内側 = ほぼ表面）。
   股関節は大腿の中心から右へ 6.6〜9.3cm、左肩は肩の中心から 6.8cm 胸の中へ、膝・足首は右へ 3.4〜4.1cm、肘は 2.0〜2.5cm（全体に体の右へずれている）。腕の長さも左 48.7cm・右 43.8cm と非対称（メッシュの腕は左右とも約 46cm）。
   関節を軸に皮膚を回すスキニングは、回転の中心がずれていると、ひねる・曲げるたびに体の片側が余計に振られる（骨盤の軸が体の右の縁にあると、左のウエストは 2 倍近い腕の長さで振られる）。
2. **重みが胴で漏れていた（左右非対称）。** 脇腹（Hips の +14〜+20cm）に**腕の骨（LeftArm）の重みが 50〜80%**、腰（ショーツの縁）に**脚の骨（LeftUpLeg）の重みが 65%**。胸の骨（`Spine`）の重みは全体で 6（使われていない）、
   `Hips` は骨盤のごく一部（左の尻に山が 1 つ）。左の肩・脚の骨が体の反対側まで重みを持つ（総重みは LeftShoulder 2797 に対し RightShoulder 201）。腕を上げる・脚を踏み出すと、離れているはずの脇腹・腰の皮膚が引かれ、腰が細く潰れ、ショーツの縁がささくれる。
3. **手付けの 2 ボーン IK は「子の位置が親のローカル +Y 軸の上にある」ことを前提にしている**（`pose-solver.ts` の `limb()` は `frameRotation(_Y, …)`）。骨の位置を動かすなら、四肢の骨の向きも子へ向け直さないと、IK の目標に手が届かない（最初の試作で左手が柄から 4cm ずれた）。

**決定**
1. **骨の位置の補正**（`tools/recenter-skeleton.mjs` + `tools/data/hero-joint-offsets.json`）: 各関節のバインド姿勢の位置を、メッシュの断面の中心（`tools/measure-joint-centers.mjs` で測る）へ寄せる。**目標の位置を絶対座標で持つ**ので、補正済みの GLB にかけても何も変わらない。
   動かすのは x だけ（骨盤〜頭 +7.8、股関節 左 +9.3 / 右 +6.6、膝 +3.4 / +4.1、足首 +3.4 / +3.6、肩 左 +6.8 / 右 +5.0、肘 +2.0 / +2.5、左手首 +3.2）。**右手首は動かさない**（剣の握り `HERO.sword` が手ボーンのローカルで調整済み）。
   - 逆バインド行列（IBM）・骨ノードのローカル位置・Hips の位置アニメーション（全キーに同じ差分）を一貫して書き換える。メッシュの頂点は触らないので、バインド姿勢の見た目は変わらない。
   - **四肢の骨（上腕・前腕・大腿・脛）のバインドの向きを、新しい子の位置へ最短の回転で向け直す**（IK の前提）。向け直した分 `D = R⁻¹·dR·R` だけ、その骨と子の回転（ノードの静止回転と全クリップの回転トラック）を共役で直す（`Q' = D_親⁻¹ · Q · D`）。
     全クリップで「バインドからの世界回転の変化」が元と同じになるので、Meshy の待機・走りなど既存の動きの意味は変わらず、**回転の中心だけが体の中心へ来る**。
2. **胴の再スキン**（`tools/reskin-torso.mjs` + `tools/lib/torso-weights.mjs`）: 胴（骨盤〜胸〜首の付け根）の重みを**位置だけの関数として作り直す**（腕・頭・髪・膝から下は元のまま。位置が同じ頂点には同じ重み）。
   - 背骨: Hips の +8.5cm（ショーツの上端）までは Hips 100%、素肌の帯（+8.5〜+24.5cm）で Hips → Spine02 → Spine01 → Spine へ連続的に移し（PoseSolver が腰・胸の回転を 0 / 1/3 / 2/3 / 1 で配るので、帯の中の回転は高さに対してなめらかに増える）、胸は Spine 100%。肩から首の付け根（+25〜+40cm）は作り直しを弱めながら Spine から neck の骨へ渡す。
   - 脚: 大腿の軸（股関節 → 膝）に沿った位置で、骨盤は Hips、大腿は UpLeg、間（股関節の上下 10cm）は連続的に混ぜる。左右は中心線からの距離で分ける。
   - 腕: **腕の軸への距離 ÷ 腕の半径 − 中心線への距離 ÷ 胴の半幅**（相対的な近さ）で胴か腕かを判定し、胴では腕の骨の重みを 0 にする。体の中心線から横に 17〜23cm 以上の頂点（腕・手・指）は元のまま（指は手首の骨から 20cm 近く先まである）。
3. **変形の崩れ度を測る道具と、資産の約束のテスト**: `tools/waist-stress.mjs`（全クリップで胴の辺の伸び・断面・ひねりを three.js のスキニングで測る。`--check` でしきい値を超えると終了コード 2）、`tools/hero-asset.test.mjs`（骨の左右対称・中心線・四肢の +Y 軸・Hips の位置トラック・腰の重みに腕脚が漏れないこと。補正前の資産では 4 項目が落ちる）、`tools/lib/torso-weights.test.mjs`。
   `tools/motion-sheet.mjs` に `--mode weights|wsum:<骨>|ybands|normals|wire`・`--no-outline`・`--tile` を足した（重みを色で見る、服の縁や関節の高さを帯で測る）。
4. **手付けのデータは 1 か所だけ**: 補正で左腕が 3cm 短くなる（48.7 → 46.7cm。右は 43.8 → 46.2cm で左右対称になる）ので、大剣のガードの握り `GUARD_HOLD.grip` の r を 0.40 → 0.36 にした（左手が柄に届かず腕が伸び切るのを防ぐ。左腕のクランプ 0）。
   大剣の構え・走りの担ぎは、待機から構えへ遷移する数フレームだけ左腕がクランプする（5 → 6、7 → 8 フレーム。もとから 5・7 フレームあった）。


`build-character.mjs` を raw から通し直したときは、その出力にこの 2 つをかける。`recenter-skeleton` は何度かけても同じ（目標の位置）。`reskin-torso` は、腕との境目の「元の重みを混ぜる帯」だけ元の重みを使うので、補正前の資産にかけること。

**検討して退けたもの**
- **Blender の自動ウェイト・ボーンの追加（ねじれ骨）**: Blender のボーンヒートはこのメッシュで失敗済み（docs/05）。ねじれ骨は不要だった（回転の中心を体の中心へ寄せ、重みを高さになめらかに作れば、背骨の 4 本で断面 0.96 を保てる）。
- **腕の判定を「腕の軸から一定距離」にする**: 脇の下では腕が胴のすぐ脇にあり（脇腹は腕の軸から 8cm、中心線から 9cm）、脇腹まで腕と判定して腕の重みが残った。相対的な近さで比べる。
- **脇の下の移り変わりを広くする**（腕の重みを肩甲骨・脇の下で広い帯に散らす）: 腕が動いたときの皮膚のずれが増えて悪化した。**作り直しの範囲を首の付け根まで延ばす**（肩の線で切ると、そこが「胸は Spine、その上は腕に引かれる」境目になり、腕を上げるたびに背中に横帯状のずれができる）のが効いた。
- **姿勢の上限（腰↔胸の相対回転を制限する）**: 手付けの技の相対回転は最大 37°（ロールの丸め 68°を除く）で、Meshy の斬り・死亡（43°）の範囲に収まっている。原因は回転量でなく回転の中心と重みだった。
- **デュアルクォータニオン・補正形状**: 断面 0.96 まで保てたので不要。描画（トゥーン・輪郭線の shader）への影響も大きい。

**代償・既知の問題**
- **実機で未確認**。確かめること: 腰まわり（大剣・片手剣の振りかぶり・踏み込み・ロール・走りでの、ショーツの縁・ウエストのくびれ・尻の形）、手が柄・盾に付く位置（腕の長さが変わった）、足の接地（足首の関節をメッシュの足の中心へ寄せた。足裏の高さは変えていない）。
- 脇の下・肩甲骨は、腕が動くと皮膚がずれる（既知の「脇のほつれ」。補正前より小さいが残る。胸の最大の伸びは 9.05 → 2.30）。首・髪（うなじの毛）は元のまま。
- 股・膝の折れ目は縮む（ロール・死亡の倒れ込み。0.12〜0.35）。見えない内側。
- 腕・脚の長さが変わるので、手付けの値（握りの r・左手の置き場）を新しく書くときは、リグから読む長さ（`rig.length`）を基準にする。
**見直し条件**: ひねりの帯（`y0` / `y1` / `ease`）を実機の見た目で調整する。ショーツの縁・尻の形が気になるなら脚の混ぜ幅（`legRamp`）。肩・脇の下が気になるなら鎖骨の動き（現状は胸に従うだけ）を足す。
